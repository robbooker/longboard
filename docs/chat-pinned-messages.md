# Pinned Messages

Ticket `fd7a8843-3a02-4e1d-b9a5-6e57bc8b92d4`, approved revision 2. Published base `6fae6cb054a94961aa18f6afbf53522400320a56`.

Admins can pin or unpin live messages in any of the eight rooms. Each room has a shared strip above its message history, visible only to users currently authorized for that room. Selecting a pin opens its original message. Personal conversation pins are unchanged.

## Storage, access and limits

The additive `chat_room_message_pins` table stores only a message reference, room, pin time and nullable pinning-account audit reference. It stores no message body, attachment, URL, or membership snapshot. Ten active pins are allowed per room, ordered by pin time descending and message UUID ascending. Repeating the same pin/unpin is idempotent; pinning an existing pin does not change its time. A full room gives an explicit instruction to unpin a message first.

The table has RLS enabled and no browser policies or privileges. New RPCs are service-only `SECURITY INVOKER` functions with empty `search_path`. Every read checks `chat_account_has_room`; mutations also check the current admin profile through the trusted account. The API independently requires `auth.user.role === 'admin'`, not merely `access.admin`. Cookie-only ShortScout sessions can have room access without gaining mutation authority. Actor IDs and admin flags from request bodies are ignored. Gainers/recording/announcement sending and reply restrictions remain unchanged, as does paused-room sending. Pins can be managed while a room is paused.

Pin mutations serialize the room's capacity with an advisory transaction lock, then acquire existing ancestor locks root first, the target message lock, and the pin row. Authorization is rechecked after any lock wait. Deletion cleanup never acquires the room capacity lock. Soft deletion/removal deletes its pin in the same transaction; physical message deletion cascades. Deliberately replacing a deleted body does not restore a removed pin. Deleting the pinning account sets its audit reference to null while retaining the shared pin. There is no new room-clear action; existing physical deletion and tombstone paths provide cleanup.

The list joins only currently authorized live message rows and their existing author identities. Edits and current member names are projected, without stored historical copies. Previews are at most 240 UTF-16 code units at the API boundary; the complete serialized response is capped at **16 KiB UTF-8**, retaining all ten IDs while shortening text if necessary. No media URL generation, preview prefetch, or per-message read is added. The new read is allowlisted in the existing batched update endpoint and reconciles through the existing ten-second coordinator cadence and room/history invalidations. No timer, scheduler, realtime publication, message event, notification event or push fanout is added.

## Navigation and coordination

Pins sit outside canonical message containers, selectors and visibility observers. Seeing a preview does not acknowledge its message or change read markers. Navigation cancels automatic opening/latest following and clears the pending opening read boundary. An older root uses the existing bounded `history?anchor=` read and retains the anchor during reconciliation. A nested pin opens that exact message as the thread original, including deep replies and replies outside a parent's latest 100 children. Drafts remain attached to their existing thread/room identity.

Read and mutation responses are fenced by account, room and generation. An opaque read-scope token prevents coordinator deduplication from reusing an old account's pending response, including A→B→A changes. Root navigation also checks a synchronous account/member/room/thread/search/DM/navigation/visibility epoch; a held pin response cannot close a thread or override search opened afterward. Skip Latest and later pin choices invalidate older jumps.

An old retained root produces 81 top-level rows. The reviewed prerequisite from Reply in Reply Count (`573f764e683665e4fa47ee63f215d9428800e80d`, applied here as `c32d6b5`) batches the existing count requests into at most 80 IDs each and combines them atomically with ownership fences. This release includes that bounded helper and the scoped PublicChat call. Nested reply-count labels remain the separate ticket's work. No truncation is used to hide the 81st root.

## Release compatibility

The migration is additive: a separate table, guarded list/mutation RPCs and an after-update cleanup trigger. Existing message schemas, message mutations, identities, room authorization, read markers, personal pins, release controls and publishing infrastructure are unchanged. Existing clients continue their normal behavior; their delete paths automatically clean any new pins. The service applies the migration before deploying the new API/UI.

The exact hashed migration is recorded in `.release/fd7a8843-3a02-4e1d-b9a5-6e57bc8b92d4.json` with `backwardCompatible: true`. Work is local only.
