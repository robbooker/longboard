# ShortScout chat session and authorization contract

Ticket: `5984803d-415c-4b20-aa5d-53acf52923d7`. Source v2 is a required deployment dependency, not included in the Longboard publisher. See the source companion's `docs/CHAT-AUTHORIZATION-RENEWAL.md` for the exact source files, digests, protocol and supervised source-first probes.

## Identity and access

A currently verified Longboard principal or an unexpired, nonrevoked local chat token resolves only its existing direct ShortScout identity or nonrevoked membership bridge. `chat_shortscout_binding` can find stale identity associations but grants no access. No identity is selected from email or client input, and no upstream password/JWT is retained.

`chat_shortscout_authorization` holds a separate authoritative v2 decision. `chat_shortscout_authorized_identity` and `chat_account_has_room` enforce exact current paid tiers, including exact Mastermind for SS, with positive proof valid for at most 60 seconds from database request reservation. The fixed source endpoint uses a five-second timeout, no redirects, signed nonce/digest binding, bounded bodies and no stale fallback. Source unavailability retains identity/session but grants no expired SS proof. A known denial remains a historical suppression until newer authoritative allow, even through later failures. Independent LB cohort/admin authorization remains intact; cookie-only identities retain role `user`.

Begin/finish RPCs use a database row lock, generation and request-context compare-and-swap. Context binds account, session token hash and bridge version. Principal/binding are rechecked after any proof-lock wait. Older responses cannot replace newer proof; unlink/local logout cannot make a delayed response restore that association/session. Only in-flight requests coalesce in-process. Cross-instance pending requests use bounded backoff, at most eight iterations with a six-second overall transport deadline; a five-second cooldown bounds unavailable retries. No new polling or fanout worker exists.

Fresh completed signed handoffs require a fresh v2 proof and mint a new 30-day **absolute** local token; HTTP-only, secure production, same-site, host-only cookie max age matches database expiry. Routine renewal never moves token expiry. Existing tokens retain their original expiry and expired/revoked tokens cannot be revived. Legacy consume remains a 12-hour issuer; delayed callbacks cannot reset captured rollout proof, erase managed denial, or reactivate a bridge revoked after the request began. Upstream SS logout is not federated to chat; supported source account bans/soft-deletes and current tier are checked at renewal.

## Actor versus offline candidate policy

Every existing actor/API/RPC access check stays on `chat_account_has_room`. The canonical `chat_shortscout_identity` remains a granting strict/captured-compatibility resolver because the published old backend uses it to authorize service-role reads; it never returns the offline recipient window. Browser RLS is unchanged: this migration grants no SS-derived browser-table access. The historical `chat_shortscout_recipient_identity` is non-granting and used only through `chat_account_room_recipient_eligible` for existing offline candidate behavior. Its positive horizon remains 12 hours, not 60 seconds and not 30 days; a known source denial suppresses it immediately.

Explicit target-only replacements cover mention/reply/announcement recipients, DM directory candidates, favorite other participants, and room member lists/counts. Reaction notification recipients use the offline helper; the reacting actor remains strict. Push target checks preserve the existing 12-hour sender/recipient candidate policy, and `prepare_chat_push_job` still rechecks the live target directly before producing an opted-in preview. Unknown upstream changes may therefore remain eligible for offline notifications/push until the historical horizon or a new observed denial; this is not globally instant upstream revocation. Content/API reads and notification read/clear actions remain strict.

## Lock behavior

Existing batched updates carry current account-scoped room permissions. The shared coordinator ignores stopped, malformed and older replies, while old servers may omit the new metadata. No additional polling is added. Single-room navigation, browser Back/Forward and lock links follow current trusted permissions. SS-only login recovery does not require a Longboard link session. An active room losing access hides its room/reply content, keeps the actor and draft, and can recover automatically; a 401 still clears session UI and returns to login. Quad retains its existing current-authority conversation options.

## Rollout and bounded recovery

Use supervised daytime release. First deploy and verify the additive ShortScout SQL and signed v2 Edge function. Record the source evidence before activating the Longboard release plan. The Longboard dedicated release service remains the sole consumer publisher; no service infrastructure/credentials/configuration changes are included.

The consumer migration captures an immutable cutoff at migration time plus **24 hours**, and every existing legacy identity's original (including already expired) `verified_at + 12 hours` horizon. Only never-managed subjects can use the captured proof, only before both limits. New application requests require v2 immediately. Managed subjects never fall back. Old callbacks do not extend either limit; a genuinely new identity created by a validated legacy handoff before cutoff gets one captured horizon, capped at first completion plus 12 hours and the fixed cutoff, only if never managed. `ON CONFLICT DO NOTHING` prevents extension. Every preexisting horizon is captured, including expired ones, so deletion/recreation cannot restore one. Legacy capability is the intersection of captured and current bound tiers: a known downgrade removes SS immediately and an old callback cannot promote beyond the captured capability. After cutoff, even a new legacy callback cannot grant access. The 24-hour window is a maximum recovery opportunity, not an entitlement extension: individual proofs may expire much earlier.

If migration succeeds but app deployment fails/deferred, existing never-managed users retain only that bounded original proof. Repair/deploy within the window. After cutoff, old SQL actor paths require fresh v2 too. Rolling back application/source does not restore managed or expired legacy access; do not reset cutoff or extend sessions/proofs. The additive migration is marked backward compatible only for this explicitly time-bounded existing-client transition. Final release review must accept that rollback limit and confirm source readiness before registration.
