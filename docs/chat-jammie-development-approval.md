# Jammie development approval

Jammie can approve the current discussion proposal for development. Rob exclusively retains approval of the exact merge/publish release version and commit. Declining, archiving, editing approved scope, and setting priorities retain their existing owner restrictions.

The additive migration adds `chat_feature_members.can_approve_development`, defaulting to false. It seeds only verified Jammie account `6ad10d99-fe91-4955-86fa-a893b9763573`, requiring its existing participant membership and trusted Longboard profile email association from the original feature migration. A read-only production membership check confirmed Jammie and another participant; participant role alone is deliberately insufficient. Missing or changed association grants nothing. No global admin role, membership, release-service function, worker claim, or publishing rule is changed.

The service-only SQL action remains the authority and rechecks membership/capability per call. Row locking, proposal revision checks, and nonempty scope checks are preserved. Approval atomically records `approved_by`, `approved_at`, `approved_proposal`, and an attributed timestamped system message. Other feature members receive the existing development status notification, respecting notification preferences and ticket mutes. The approver does not receive a self-notification. UI uses server-returned capability and shows approval time alongside approved scope; Codex planning instructions distinguish development from release approval.

Migration deployment is pinned by digest in `.release/655f6c64-b31e-4ca4-ae58-62bb8c847298.json`. It is compatible with the previous application: existing columns/functions remain, the new column defaults false, and the previous UI continues its owner-only presentation until deployment. Apply through the dedicated release service before the new application. No production migration or release action was performed during development.
