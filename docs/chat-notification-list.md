# Notification List

Ticket `10b2d79b-2d45-4fbf-9e65-774124714464`, approved revision 2. Initial published base: `6d17c54776cf2fa4648cadd85627f37a687d5d27`.

Read chat alerts remain in the recent notification list with a visible **Read** label and lighter type. Their navigation opens the current message/conversation directly without a redundant manual acknowledgement. Unread controls and observed-boundary reads remain intact. Missing optional `read` flags from an older server mean unread. Direct messages remain one row per conversation: the latest eligible incoming message supplies the preview and `unread: 0` identifies a read row. Outgoing messages do not replace that preview.

This is a bounded recent list, not a permanent archive. The existing 50 room-alert, 100 conversation and 50 reaction sample limits remain, followed by the existing 32 KiB UTF-8 response bound. Every unread total, room map, pinned conversation count and observed event cursor still comes only from eligible unread events, including events outside the listed sample. A read row's higher sequence cannot advance mark-all boundaries. Redundant older-client read requests remain idempotent and cannot clear events newer than the observed cursor. Feature notifications already retain read entries and their implementation is unchanged.

The migration adds a service-only reaction history projection with the same current authorization as the unread helper. It leaves `eligible_chat_reaction_notifications` and all read RPCs unchanged. The inbox uses live target/name joins, including strict ShortScout access, room entitlement, participant/status, symmetric blocks, and target deletion/removal rules. Deactivated reactions disappear; reactivation creates the existing fresh event ID/sequence. Deleted or inaccessible targets do not retain content snapshots. Two recipient/recent indexes support the history reads. There is no backfill, new delivery, timer or poller.

The activity hook hides old account/member snapshots immediately and fences late responses and successful reads. An actual hook/coordinator test reproduced the old literal-URL race: replacing the owner while the old GET was held made the new owner join that old request. A stable opaque per-mounted-owner query token prevents the join, including A→B→A, without encoding identity or changing authorization. The shell's existing activity context shares this hook across its panes; batching and reconciliation stay with the existing coordinator. Successful read mutations invalidate earlier GET results, and an old owner's completed POST cannot report navigation success in the new session.
