The creator can delete their own unsubmitted ticket from its detail actions. The exact confirmation is **“Are you sure you want to delete this ticket?”**, with Cancel and Confirm. Cancel and Escape preserve the ticket and unsaved input. Confirm removes the eligible ticket and its discussion, then returns to Active while preserving title search, selected archive ordering, and unrelated new-ticket input.

## Eligibility and database behavior

There is no separate submission action in the existing lifecycle. The approved interpretation is strictly `discussion` (shown as “Discussion · pending”), with all approval fields null, no claim time or worker token, no archive metadata, no outcome, and no release row in any state. A saved, nonempty proposal can still qualify before approval. Declined, archived, approved, working, blocked, ready and published requests cannot qualify. No new lifecycle or owner override is introduced.

`can_delete_chat_feature(actor, feature, expected_revision)` checks current private feature membership, exact creator and revision, and every exclusion above. The full selected-detail GET calls it once and returns an optional `canDelete` boolean. It does not expose creator IDs, worker tokens, or new directory data; list and two-second status reads do not call it. Missing or failed capability reads fail closed while the existing private detail remains readable. The API ignores caller actor/role fields, requires the verified private-channel session and allowed origin, explicit `confirmed: true`, canonical UUID, and a positive bounded integer revision.

`delete_chat_feature` takes the same request `FOR UPDATE` lock used by editing, approval, archive and release registration, then rechecks the capability. An earlier edit invalidates a stale revision, while earlier approval/archive/registration makes deletion ineligible. A successful delete makes later mutations observe a missing request. Existing foreign keys atomically remove only that request's messages, notifications and notification mutes. The function never deletes a ticket with a release, even an inconsistent discussion row with a release. It creates no message, notification, push or work event.

Both new functions are service-only `SECURITY INVOKER`, with empty `search_path` and schema-qualified relations/function calls. No existing table grants, policies, publisher/claim/approval functions or triggers are replaced. The database suite compares those function definitions before and after the migration and operations.

## Browser behavior and response fencing

The button exists only on an eligible selected detail. Native modal semantics keep focus inside the dialog, initially on Cancel. Keyboard confirmation and Escape are supported. The confirmation captures the exact revision when opened, so a changed proposal must be reviewed again rather than silently deleting a newer revision.

The authorized server page keys the component by the viewer's own account ID. That ID scopes UI state and is never accepted by the mutation as authority. Unmount aborts the local pending delete response. Full-read keys include the viewer, selection, view, order, search and page; existing status-response fences remain intact. Deletion invalidates older reads and keeps a local set of successfully removed UUIDs so a delivered old snapshot cannot restore a deleted row. The acknowledgment clears only its own selected detail and draft; another ticket selected while it was pending keeps its draft. Existing polling, priority ordering, archive dates, search and URL behavior are unchanged.
